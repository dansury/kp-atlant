# Feature Specification: Atlant Armour КП Automation System

**Created**: 2026-08-25  
**Status**: Draft  
**Input**: Веб-сервис для автоматизации формирования коммерческих предложений (КП). Считывает запросы с email, ищет товары в МойСклад, формирует брендированный PDF, уведомляет менеджера, позволяет дописать текст, самообучается на корректурах. Включает CRM-модуль, систему аккаунтов менеджеров, допродажи, интеграцию с МойСклад для создания заказов.

---

## User Scenarios & Testing

### User Story 1 — Менеджер получает готовый черновик КП по входящему запросу (Priority: P1)

Клиент отправляет email-запрос на info@atlant-armour.ru с просьбой выставить КП на определённые товары. Система автоматически считывает письмо (через IMAP к smtp.spaceweb.ru:465 SSL), извлекает из текста: название организации, контактное лицо, запрашиваемые позиции и количества. По каждой позиции обращается к API МойСклад — находит товар по названию (fuzzy-match), получает цену, остаток на складе, статус резерва, характеристики. Формирует брендированный PDF-файл КП (логотип, реквизиты юрлица, таблица позиций с ценами/НДС/суммой, стандартные условия поставки) и черновик сопроводительного текста письма. Менеджер получает browser push-уведомление «Новый запрос на КП от [Организация]». Открывает веб-интерфейс, видит: исходное письмо, сформированный PDF (preview), черновик ответного письма. Может отредактировать текст в специальном поле (добавить характеристики товара, условия доставки, комплектацию), подтвердить или скорректировать позиции. Нажимает «Сохранить КП» — PDF пересоздаётся с финальным текстом. Нажимает «Отправить» — письмо с PDF-вложением уходит клиенту с адреса info@atlant-armour.ru.

**Why this priority**: Это core-функция, ради которой строится вся система. Без неё остальное бессмысленно.

**Independent Test**: Отправить тестовое письмо на info@atlant-armour.ru с запросом «Прошу выставить КП на 10 шт. аптечка Лазарь Multicam и 5 шт. шлем Атом-2 размер M». Система должна: распознать 2 позиции, найти их в МойСклад, сформировать PDF с корректными ценами и суммами, уведомить менеджера.

**Acceptance Scenarios**:

1. **Given** письмо с запросом на 3 позиции, **When** система обрабатывает его, **Then** PDF содержит 3 строки в таблице с ценами из МойСклад, итоговую сумму, НДС, логотип, реквизиты.
2. **Given** товар в запросе не найден точно в МойСклад, **When** fuzzy-match находит ближайшее совпадение, **Then** система показывает менеджеру варианты для подтверждения и не подставляет автоматически.
3. **Given** товар найден но остаток = 0, **When** формируется КП, **Then** позиция помечена «под заказ» и менеджер видит предупреждение.
4. **Given** менеджер добавляет текст про комплектацию под таблицей, **When** нажимает «Сохранить КП», **Then** PDF содержит этот текст между таблицей и условиями поставки.
5. **Given** менеджер не реагирует на push-уведомление >24ч, **When** проходят сутки, **Then** email-уведомление уходит на atlant.armour@yandex.ru.

### User Story 2 — Копипаст запроса вручную (Priority: P1)

Менеджер заходит в веб-интерфейс, копирует текст запроса из любого источника (мессенджер, другой email, звонок), вставляет в поле ввода. Система обрабатывает текст так же, как email: извлекает позиции, ищет в МойСклад, формирует КП.

**Why this priority**: Не все запросы приходят на info@. Ручной ввод — must-have с первого дня.

**Independent Test**: Вставить текст «Нужно 20 жгутов-турникетов CAT и 20 окклюзионных пластырей». Система находит товары, формирует PDF.

**Acceptance Scenarios**:

1. **Given** текст запроса без названия организации, **When** менеджер вставляет его, **Then** система просит ввести название контрагента вручную.
2. **Given** текст на русском со свободной формулировкой, **When** LLM парсит его, **Then** извлечены корректные наименования и количества.

---

### User Story 3 — Система аккаунтов менеджеров и CRM (Priority: P2)

Каждый менеджер логинится под своим аккаунтом. Внутри видит: входящие запросы (назначенные ему или общий пул), историю переписки по каждому контрагенту, статус сделки, отправленные КП. Поиск и фильтрация по контрагентам, датам, статусам.

**Why this priority**: Без аккаунтов система работает для одного менеджера. Масштабирование — следующий шаг после MVP.

**Independent Test**: Два менеджера логинятся с разными аккаунтами. Менеджер А видит свои сделки и не видит сделки менеджера Б (кроме общего пула).

**Acceptance Scenarios**:

1. **Given** новый запрос в общем пуле, **When** менеджер А нажимает «Взять в работу», **Then** запрос закрепляется за ним и пропадает из пула.
2. **Given** переписка с контрагентом из 5 писем, **When** менеджер открывает карточку контрагента, **Then** видит всю цепочку с датами и КП.
3. **Given** контрагент есть в МойСклад (по ИНН), **When** система находит его, **Then** подтягивает контактные данные, историю заказов.

---

### User Story 4 — Самообучение и база знаний (Priority: P2)

Когда менеджер корректирует автосгенерированный текст (сопроводительное письмо, комментарий в КП), система сохраняет пару «было → стало» в базу знаний. При генерации следующего текста LLM использует накопленные примеры корректур как few-shot examples. Со временем черновики становятся точнее и реже требуют правок.

**Why this priority**: Самообучение — ключевое конкурентное преимущество системы, но работает только после накопления данных из US1.

**Independent Test**: Создать 5 КП с корректурами (добавление «самовывоз в г. Москва»). На 6-м КП с аналогичным контекстом система должна сама предложить текст про самовывоз.

**Acceptance Scenarios**:

1. **Given** 10 корректур где менеджер добавлял «доставка ТК до адреса», **When** новый запрос содержит адрес доставки, **Then** черновик автоматически включает текст про доставку.
2. **Given** база знаний содержит 50 пар «было → стало», **When** новое КП генерируется, **Then** LLM-промпт включает 5 самых релевантных примеров.

---

### User Story 5 — Создание заказа в МойСклад одной кнопкой (Priority: P2)

После отправки КП и подтверждения сделки менеджер нажимает «Создать заказ в МойСклад». Система запрашивает логин менеджера в МойСклад (для привязки заказа), создаёт заказ покупателя через API с позициями из КП, прикрепляет ссылку на переписку в CRM в комментарии к заказу.

**Why this priority**: Закрывает цикл «запрос → КП → заказ» внутри одной системы.

**Independent Test**: Из подтверждённого КП на 3 позиции создать заказ в МойСклад. Проверить: позиции, количества, цены совпадают. В комментарии — ссылка на CRM.

**Acceptance Scenarios**:

1. **Given** КП на 3 позиции подтверждено менеджером, **When** нажимает «Создать заказ», **Then** в МойСклад появляется заказ с правильными позициями и контрагентом.
2. **Given** контрагента нет в МойСклад, **When** создаётся заказ, **Then** система предлагает создать контрагента (ИНН, название, контакт) или выбрать существующего.

---

### User Story 6 — Письма допродажи (Priority: P3)

Система анализирует историю переписки: если клиент запрашивал КП, но заказ не состоялся (по данным МойСклад — нет заказа с таким контрагентом за 30 дней), предлагает менеджеру отправить follow-up письмо. Текст письма генерируется по правилам из EMAILRULES.md с учётом ToV из GRAPH. Менеджер видит черновик, может отредактировать и отправить.

**Why this priority**: Допродажи важны, но возможны только когда основной цикл работает стабильно.

**Independent Test**: Контрагент запросил КП 35 дней назад, заказ не создан. Система предлагает follow-up. Текст соответствует ToV.

**Acceptance Scenarios**:

1. **Given** КП отправлено 30+ дней назад и заказа нет, **When** система проверяет статусы, **Then** в интерфейсе менеджера появляется карточка «Предложить follow-up» с готовым черновиком.
2. **Given** EMAILRULES.md обновлён через интерфейс, **When** следующий follow-up генерируется, **Then** текст учитывает новые правила.

---

### User Story 7 — Оценка сделки по данным МойСклад (Priority: P3)

Система по ИНН / названию контрагента и составу запроса сопоставляет данные из МойСклад (заказы, отгрузки, оплаты). Показывает менеджеру статус: «Сделка состоялась», «В процессе», «Не закрыта», «Повторный клиент». Помогает приоритизировать работу.

**Why this priority**: Аналитика — усиление CRM, не блокирует core flow.

**Independent Test**: Контрагент с ИНН из МойСклад, у которого есть 2 оплаченных заказа. Система показывает «Повторный клиент, 2 заказа на сумму X».

---

### Edge Cases

- Письмо на нескольких языках (русский + английский термины товаров)
- Запрос без конкретных позиций («нужны средства защиты для отряда 30 человек»)
- Один email содержит несколько запросов от разных отделов
- Товар есть в МойСклад но с другим написанием (транслитерация, сокращения)
- Менеджер удаляет позицию из КП, которая была в запросе
- Цена в МойСклад изменилась между формированием КП и отправкой
- Клиент запрашивает нестандартный НДС (0%, 20%)
- Большой заказ (50+ позиций) — PDF на несколько страниц

## Requirements

### Functional Requirements

- **FR-001**: Система MUST получать письма через IMAP (smtp.spaceweb.ru:465 SSL) и парсить текст запроса.
- **FR-002**: Система MUST принимать текст запроса через веб-интерфейс (копипаст).
- **FR-003**: Система MUST извлекать из текста запроса: наименования товаров, количества, название организации, контактное лицо, условия доставки.
- **FR-004**: Система MUST искать товары в МойСклад по API (fuzzy-match по названию) и получать: цену, остаток, характеристики, статус резерва.
- **FR-005**: Система MUST формировать PDF-файл КП: логотип Atlant Armour, реквизиты юрлица (настраиваемые), таблица (№, наименование, ед.изм., кол-во, цена с НДС, сумма), итого, условия поставки, дата, подпись.
- **FR-006**: Система MUST позволять менеджеру добавлять/редактировать текстовый блок в КП (характеристики, комплектация, условия доставки).
- **FR-007**: Система MUST генерировать черновик сопроводительного текста письма с помощью LLM (OpenRouter / Yandex FM).
- **FR-008**: Система MUST отправлять browser push-уведомления менеджерам при новых запросах.
- **FR-009**: Система MUST отправлять email-уведомление на atlant.armour@yandex.ru если нет реакции менеджера >24ч.
- **FR-010**: Система MUST поддерживать аккаунты менеджеров с логином/паролем.
- **FR-011**: Система MUST хранить историю переписки по каждому контрагенту (CRM).
- **FR-012**: Система MUST сохранять корректуры менеджеров и использовать их как контекст для будущих генераций.
- **FR-013**: Система MUST создавать заказ покупателя в МойСклад через API (по нажатию кнопки, с привязкой к менеджеру).
- **FR-014**: Система MUST генерировать follow-up письма для несостоявшихся сделок по правилам EMAILRULES.md.
- **FR-015**: Система MUST позволять менять реквизиты юрлица в PDF через настройки интерфейса.
- **FR-016**: Система MUST оценивать статус сделки по данным МойСклад (заказы, оплаты, отгрузки).
- **FR-017**: Система MUST отправлять готовое КП с PDF-вложением с адреса info@atlant-armour.ru через SMTP (smtp.spaceweb.ru:465 SSL; также 25/2525 STARTTLS).
- **FR-018**: Система MUST позволять редактировать EMAILRULES.md из веб-интерфейса с LLM-анализом правил.
- **FR-019**: Система MUST поддерживать настраиваемый % НДС (5%, 0%, 20%) на уровне позиции и документа.
- **FR-020**: Система MUST показывать preview PDF в браузере перед отправкой.
- **FR-021**: Подтверждение КП MUST быть утверждением о документе, а не кликом (модуль 018): КП, в котором есть позиция с нулевой или отсутствующей ценой — либо нет ни одной позиции, — отклоняется один раз с перечислением этих позиций и уходит только по явному второму ответу менеджера. Ответ сохраняется на КП и аннулируется последующей правкой цены. Наглухо не блокируется: КП «цена по запросу» — нормальный документ.
- **FR-022**: Позиции запроса, которым не нашлось совпадения в каталоге, MUST быть названы клиенту дословно его же словами — отдельным блоком в КП и в черновике ответа, — а не пропадать молча (модуль 018). Строка, подтверждённая менеджером вручную, дырой не считается.
- **FR-023**: Внутри одного КП товар MUST называться одним именем: сопроводительное письмо берёт названия из таблицы позиций КП, а не из запроса клиента и не из базы знаний (модуль 018).
- **FR-024**: E-mail адрес MUST NOT печататься как название покупателя в КП (модуль 018). Название организации ищется в подписи и цитируемых фрагментах письма, затем регэкспом по тексту; если его всё равно нет — документ печатает «Покупатель уточняется», а менеджер видит, какую карточку дозаполнить.

### Non-Functional Requirements

- **NFR-001**: Стек: PHP 8.1+ / SQLite / vanilla JS. Деплой на shared-хостинг без Docker.
- **NFR-002**: LLM-интеграция через двухпровайдерный wrapper (OpenRouter + Yandex FM) из NeuroPro — fallback-chain, retry, json-mode.
- **NFR-003**: Время генерации КП (от получения письма до готового PDF) — не более 30 секунд при наличии данных в МойСклад.
- **NFR-004**: PDF MUST выглядеть профессионально: чистая типографика, брендированный заголовок, чёткая таблица. Минимализм в лучших традициях российского B2B.
- **NFR-005**: Веб-интерфейс MUST быть адаптивным (desktop + mobile).
- **NFR-006**: Все чувствительные данные (API-ключи, пароли SMTP) хранятся в серверных настройках, не в коде.
- **NFR-007**: Система MUST работать за HTTPS (настраивается на уровне хостинга).
- **NFR-008**: База знаний (корректуры) MUST быть доступна для экспорта (JSON).

## Key Entities

- **Запрос (Request)** — входящий запрос на КП (из email или ручного ввода). Содержит: источник, текст, разобранные позиции, контрагент, статус обработки.
- **Контрагент (Counterparty)** — организация или лицо. ИНН, название, контакт, привязка к МойСклад.
- **КП (Proposal)** — сформированное коммерческое предложение. Позиции, суммы, текст, PDF-файл, статус (черновик / отправлено / заказ создан).
- **Позиция КП (ProposalItem)** — строка таблицы. Товар из МойСклад, количество, цена, НДС, сумма.
- **Менеджер (Manager)** — пользователь системы. Логин, email, привязка к МойСклад.
- **Переписка (Correspondence)** — цепочка писем по запросу. Входящие + исходящие + внутренние заметки.
- **Корректура (Correction)** — пара «автотекст → текст менеджера» с контекстом (тип запроса, контрагент, товары).
- **Правила email (EmailRules)** — EMAILRULES.md, редактируемый из интерфейса. Правила ToV и email-маркетинга для follow-up.
- **Настройки юрлица (LegalEntity)** — ИП/ООО, ИНН, ОГРН/ОГРНИП, адрес, подписант, город.

## Success Criteria

- **SC-001**: Менеджер формирует КП от момента получения запроса до отправки PDF за ≤ 3 минуты (vs. текущие 15–30 минут).
- **SC-002**: После 50 обработанных КП система генерирует черновики, требующие правок менее чем в 30% случаев.
- **SC-003**: PDF визуально неотличим от профессионального КП, созданного вручную — с логотипом, корректной таблицей, подписью.
- **SC-004**: 100% позиций с точным совпадением в МойСклад автоматически заполняются без ручного ввода.
- **SC-005**: Ни одно КП не уходит клиенту без подтверждения менеджером. Подтверждение содержательно: КП с нулевой ценой или без позиций требует явного второго ответа, который записывается (FR-021).
- **SC-006**: Система развёрнута на shared-хостинге без привлечения DevOps.

---

## Out of Scope

- Чат-бот для клиентов (не нужен, система для внутреннего использования менеджерами).
- Интеграция с 1С напрямую (через МойСклад как прокси).
- Мобильное приложение (веб-интерфейс адаптивный, достаточно).
- Автоматическая отправка КП без подтверждения менеджером (нарушает Constitution I).
- Генерация договоров и счетов (только КП).
- Приём оплат и бухгалтерские операции.
- Obsidian-хранилище (заменено встроенной базой знаний с аналогичной функцией).

---

## Assumptions

- Email info@atlant-armour.ru доступен через IMAP на smtp.spaceweb.ru:465 (SSL). Логин и пароль будут предоставлены при деплое.
- МойСклад API (JSON API 1.2) доступен по токену. Текущий токен: рабочий, доступ к товарам, заказам, контрагентам.
- OpenRouter API-ключ и/или Yandex Foundation Models API-ключ будут предоставлены при деплое.
- Хостинг поддерживает PHP 8.1+, cURL, mbstring, SQLite3, allow_url_fopen.
- Менеджеров не более 10 человек (SQLite справится).
- Среднее количество позиций в КП: 1–10 (редко больше).
- Юрлицо на данный момент: ИП Сурков К. А. (ИНН 773135420168, ОГРНИП 320774600452996, г. Москва). Может измениться — настраивается.

## Паттерны КП (выявленные из образцов)

### Структура PDF (единообразная по всем 10 образцам):

1. **Шапка**: «от: ИП Сурков К. А., ИНН ..., ОГРНИП ..., г. Москва» — правый верхний угол.
2. **Заголовок**: «КОММЕРЧЕСКОЕ ПРЕДЛОЖЕНИЕ» — по центру.
3. **Вступление**: «По Вашему запросу ИП Сурков Кирилл Александрович имеет возможность поставить следующее вещевое имущество:»
4. **Опциональный блок перед таблицей**: условия отгрузки (самовывоз — КП Компьютек).
5. **Таблица**: № | Наименование | Ед.изм. | Кол-во | Цена за единицу, в т.ч. НДС 5% | Сумма.
6. **Итого**: под таблицей. Опционально «в т.ч. НДС: X руб.» (КП Газпром).
7. **Опциональный блок после таблицы**: комплектация (КП Фосфорит — «В комплект к каждому шлему включены: ...»).
8. **Условия поставки**: стандартный текст (стоимость, расходы, хранение, погрузка, страхование...). Варианты: + доставка ТК до адреса (КП Газпром).
9. **Сроки**: «Сроки выполнения условий договора X календарных дней» (10 или 30).
10. **Срок действия**: «Предлагаемая цена... является твёрдой и не подлежит изменению в течение 14 дней...»
11. **Дата и подпись**: «ДД.ММ.2026г. [подпись] Сурков Кирилл Александрович».

### Вариативные элементы (что меняет менеджер):

- Позиции, количества, цены, % НДС (5% в большинстве, выделенная сумма НДС — опционально)
- Срок исполнения (10 или 30 дней)
- Текст про доставку / самовывоз (перед или после таблицы)
- Текст про комплектацию товара (после таблицы)
- Строка «в т.ч. НДС» (присутствует не всегда)

## Clarifications (resolved 2026-08-25)

### C-001: PDF-библиотека
**Decision**: mPDF  
**Rationale**: HTML→PDF подход позволяет верстать шаблон КП через HTML/CSS — быстрее итерировать дизайн, чем программно через TCPDF. Хорошая поддержка кириллицы, таблиц, встроенных шрифтов. Средний вес, не требует внешних зависимостей типа wkhtmltopdf. На shared-хостинге работает из коробки.  
**Alternatives rejected**: TCPDF (мощнее, но сложнее верстать), Dompdf (хуже с точным позиционированием), FPDF (требует ручной настройки кириллицы).

### C-002: Push-уведомления
**Decision**: SSE/polling в открытой вкладке + email fallback через 24ч  
**Rationale**: Shared-хостинг — нет возможности держать Service Worker / VAPID. Менеджеры работают с открытой вкладкой CRM. JS-polling каждые 30 секунд проверяет `/api/notifications.php`. Если менеджер не отреагировал за 24ч — email на atlant.armour@yandex.ru (уже в спеке). Zero config, zero infrastructure.  
**Upgrade path**: При переходе на VPS можно добавить Web Push API поверх без ломки архитектуры.

### C-003: Fuzzy-match порог
**Decision**: Средний (>60% similarity), показывать до 3 вариантов  
**Rationale**: Запросы часто содержат сокращения («бж» = бронежилет), транслитерацию, неточные названия. При >80% слишком много промахов. При >40% слишком много шума. 60% — баланс: система показывает 1-3 кандидата, менеджер подтверждает. Если ровно 1 совпадение >90% — подставляется автоматически (менеджер видит, может изменить). Если 0 совпадений — ручной поиск из каталога.  
**Algorithm**: Levenshtein distance + нормализация (lowercase, убрать кавычки/скобки, «шт.»→«»). LLM-парсер предварительно нормализует названия из запроса.

### C-004: МойСклад API scope
**Decision**: Реализовать с runtime-проверкой прав  
**Rationale**: Неизвестно, какой scope у текущего токена. При старте приложения вызов `GET /api/remap/1.2/entity/customerorder` — если 403, US5 (создание заказов) отключается gracefully (кнопка «Создать заказ» → «Нет прав API»). Чтение товаров/контрагентов проверяется отдельно — без него система не стартует.  
**Impact**: US5 и US7 могут быть недоступны при read-only токене. Core pipeline (US1, US2) работает при read-only.

### C-005: EMAILRULES.md
**Decision**: Создаётся при первом деплое с дефолтным содержимым  
**Rationale**: В спеке EMAILRULES.md упомянут как настраиваемый, но нигде не описан его формат. Система генерирует default при первом запуске на основе ToV из tov.md. Менеджер может редактировать через веб-интерфейс (FR-018). Формат: markdown с секциями «Тон», «Структура follow-up», «Запрещённые слова», «Примеры».

### C-006: Интервал IMAP-polling
**Decision**: Каждые 2 минуты (cron-задача или long-poll на shared-хостинге)  
**Rationale**: Shared-хостинг обычно имеет cron с минимальным интервалом 1 мин. 2 минуты — разумный баланс между оперативностью и нагрузкой. Альтернатива: менеджер вручную нажимает «Проверить почту» в интерфейсе (мгновенно).

### C-007: NeuroPro LLM-wrapper
**Decision**: Использовать lib/llm.php из NeuroPro-main.zip как отправную точку  
**Rationale**: В claude.md указано: «Use OpenRouter + Yandex Foundation Models wrapper from NeuroPro (lib/llm.php pattern)». NeuroPro-main.zip лежит в папке проекта. Извлечь оттуда LLM-обёртку, адаптировать под нужды КП-системы (json-mode для парсинга запросов, text-mode для генерации писем).

### C-008: Подпись в PDF
**Decision**: Растровое изображение подписи, загружаемое через настройки  
**Rationale**: В образцах КП подпись — сканированная. Менеджер загружает PNG/JPG подписи через настройки юрлица. Если не загружена — текстовая заглушка «_____ / ФИО».
